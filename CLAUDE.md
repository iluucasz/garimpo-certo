## Architecture: backend, auth, storefront and the admin panel are all real (Neon). Nothing is mock and nothing lives in localStorage except per-visitor preferences

As of 2026-09-04 the mock→real migration landed for the backend (`app/api/v1/*`, auth, admin RBAC) **and** the storefront rendering path (`app/page.tsx`, `app/produto`, `app/categorias`, `app/buscar`, `app/comparar`, `app/favoritos`/`historico`). The real Neon schema didn't originally have several fields the storefront needs (`rating`/`reviewsCount`/an editorial `score`/`growth` at product level — only offer-level `rating` existed, and that was unpopulated) — rather than fake these client-side, they were added as real, persisted columns on `products` (see `lib/db/schema.ts`, migration `0004_noisy_tenebrous.sql`) and backfilled by `pnpm db:seed-catalog` (`lib/db/seed-catalog-enrichment.ts`), which also seeds categories, brands, one primary image, and 6 months of `price_history` per offer for the 12 real products (the DB otherwise had bare name/slug/price with no images/categories/brands/tags — check before assuming enrichment happened on a fresh clone/branch).

**Data flow**: `app/layout.tsx` (async Server Component) calls `getStoreCatalog()` (`lib/db/repositories/store-catalog.ts`, cached across requests for 5 min with tag `catalog`; the import worker invalidates it through `/api/v1/cron/revalidate`), which joins products/offers/providers/categories/brands/images/tags/price_history into shapes that match `lib/types.ts`'s original mock `Product`/`Offer`/`Provider`/`Category` types almost exactly — this was a deliberate adapter-pattern choice so that existing client components didn't need their rendering logic rewritten, only their data *source*. That catalog is passed into `<StoreDataProvider>` (`components/store-data-provider.tsx`), a React Context read by `useStoreData()` — client components (`ProductCard`, `ProductDetail`, `HomeCatalog`, `SearchExperience`, `SavedProducts`, `/comparar`) call this hook instead of importing arrays from `lib/mock-data.ts`. Server Components that need data before/outside the React tree (`generateStaticParams`, `generateMetadata`, `sitemap.ts`) call `getStoreCatalog()` directly. `lib/recommendation/engine.ts#generateRecommendations()` takes a second `catalog: {products, offers, metrics?}` argument; it no longer falls back to `lib/mock-data` — with no catalog it returns zero recommendations. Every caller (`ProductDetail`, `/api/v1/recommendations`, the ranking preview in `components/admin/settings-form.tsx`) passes the real catalog plus `metrics` from `lib/db/repositories/product-metrics.ts#getProductMetrics()` (views/clicks/favorites/conversions aggregated from `analytics_events` + `affiliate_clicks` + `affiliate_conversions`). `app/layout.tsx` loads those metrics alongside the catalog and passes them to `<StoreDataProvider metrics>`, so client components rank with measured engagement. Where no traffic has been measured yet the engine falls back to the offer's real `soldCount`/`commissionRate` instead of the hashed pseudo-random features it used before (`ALGORITHM_VERSION` is now `garimpo-ranker-3.0.0`).

### Catalog comes from the real Shopee Affiliate API

`lib/providers/shopee/client.ts` talks to `https://open-api.affiliate.shopee.com.br/graphql` (GraphQL, signed with `SHA256(AppId + Timestamp + Payload + Secret)`; credentials in `SHOPEE_AFFILIATE_APP_ID`/`SHOPEE_AFFILIATE_APP_SECRET`, server-only, retries on HTTP 429/5xx and on GraphQL code `10030`). `fetchProductOffers`/`fetchAllProductOffers` wrap `productOfferV2`; `generateShortLink` wraps the mutation (available, not used by the importer yet — `offerLink` from the API is already an attributed affiliate link).

`pnpm db:import-shopee [--per-category=24 --min-rating=4.5 --min-sales=50 --max-per-shop=2 --prune --replace-demo]` (`lib/db/import-shopee.ts`) builds the catalog per storefront category from three kinds of Shopee search (`categoryGroups` in `lib/providers/shopee/import.ts`): popular keywords, `premiumKeywords` (the main product of a higher price range) and `shopeeCategoryIds` (Shopee's internal category ids from `productCatIds`, which return the product itself instead of accessories, e.g. 101073 = consoles). Selection is **by price tier** (`lib/providers/shopee/selection.ts`, pure and unit-tested): each category fills quotas per tier (`até R$ 99` / `R$ 100–499` / `a partir de R$ 500`; 40/35/25% by default, 15/35/50% for the high-ticket categories games, eletrônicos and eletrodomésticos), with quality cut-offs per tier (rating >= 4.5; sales >= 50/30/15), at most `maxPerShop` items per seller, no repeated product name per category. Cheap tier is ranked by sales; the two higher tiers by sales x commission per sale, because sorting everything by sales fills the catalog with R$ 5 accessories (a PS5 pays ~R$ 270 per sale, a cheap earbud ~R$ 1). The visitor-facing Índice Garimpo never uses commission. `ImportOptions.dryRun` selects without writing to the DB (use it to preview). Mapping goes through `lib/providers/shopee/mapping.ts` and upserts through `lib/db/repositories/catalog-import.ts` (brand=seller, one primary image, tags derived from the numbers, `price_history` snapshot when the price moved; products are written 4 at a time, categories are created first because the table has no unique slug). `--replace-demo` **archives** (status `removed`, never deletes) products with no affiliate offer; `getStoreCatalog()` only reads `status = 'active'` rows.

Gotchas the API imposes, don't "fix" them by inventing data:
- There is no review count and no description — `products.reviewsCount` stays 0 and the UI hides review counts; `description` is generated as "Vendido por {loja} na Shopee.".
- `priceDiscountRate` only reconciles with `priceMin` when `priceMin === priceMax`; otherwise it refers to another variant, so `originalPriceFrom()` returns null (no fake "de/por"). `offers.price_max` (migration `0005_unique_falcon.sql`) stores the range so the UI can say "até R$ X".
- Shipping is not exposed at all: `Offer.shipping` is 0 as a calculation placeholder and no screen claims "Frete grátis".
- `products.editorialScore` ("Índice Garimpo") is computed by `editorialScoreFrom()` from rating + log(sales) + discount; `growthPercentage` has no source and stays 0 (sorting that used it now uses `soldCount`).

**Nothing is mock anymore.** The homepage's "Escolha pelo que importa" block (`components/home/home-selections.tsx`) is derived from the real catalog and links to `/buscar` filters; `lib/catalog/signals.ts` is the single source for those filter criteria (`matchesSignal`/`currentPrice`), shared with `components/search/search-experience.tsx` so counts and results never diverge. Collections and guides are computed from the catalog (see Operations). The admin panel is documented in **Admin panel** below. `lib/mock-data.ts` only keeps a few formatters' leftovers; do not add data there.

### Schema coverage: 47 tables exist, ~22 are actually wired up

Don't assume a table being defined in `lib/db/schema.ts` means something uses it — the DB was introspected whole, and roughly half its tables have zero references outside `schema.ts`/`relations.ts`. Before building a feature, `grep` for the table name first. As of this writing, unused: `affiliateLinks`/`affiliatePrograms` (we call `affiliateClicks`/`affiliateConversions` directly with a bare `providerId`, no link/program layer; tagged links live in `offers.affiliate_url`/`affiliate_sub_ids`), `syncJobs`/`syncJobRuns`/`syncErrors` (provider sync uses the generic `jobQueueEntries` instead), `productVariants`, `offerPrices`/`offerAvailability`/`offerCommissions` (fields live directly on `offers` instead of these normalized snapshot tables), `providerAccounts`/`providerCapabilities`, `privacyPreferences` (LGPD — see *LGPD requests and consent* below for `consentRecords`/`privacyRequests`, now wired), `anonymousIdentities`/`identityMerges`, `dailyProductMetrics`/`hourlyProductMetrics` (rollups are computed on the fly from `analyticsEvents` in `/api/v1/analytics/rollups` instead of precomputed), `auditLogs`, `globalSettings`.

Recently wired up (previously on this unused list): `productAttributes`/`productAttributeValues` (seeded by `pnpm db:seed-catalog`, joined into `Product.specs` by `getStoreCatalog()`), `providerProductMappings` (persisted by `lib/db/repositories/matching.ts#recordProviderProductMapping()` from both `POST /api/v1/matching` and the provider sync route — `productId` is `NOT NULL` on this table, so a mapping is only written when there's at least one match candidate; zero-candidate "new product" cases can't be persisted here until a product exists to point at), `wishlists`/`wishlistItems` (see below).

### Favorites: localStorage for anonymous visitors, `wishlists` table once logged in

`components/visitor-state-provider.tsx`'s `favorites` state (`useVisitorState()`) is dual-backed. Anonymous: `localStorage` only (`garimpo:favorites`), unchanged from before. Logged in: on session appearing, it fetches `GET /api/v1/wishlist`, merges in any local-only favorites via `POST /api/v1/wishlist` (one-time migration keyed by `syncedUserId` ref so it doesn't repeat), and from then on `toggleFavorite()` calls `POST /api/v1/wishlist/toggle` — the DB (via `lib/db/repositories/wishlist.ts`, one auto-created "Favoritos" wishlist per user) becomes the source of truth until the next full page load. Logging out mid-session doesn't revert the in-memory state to `localStorage` until a reload — a known, low-priority gap.

What's real now:
- **`lib/db/schema.ts`/`lib/db/relations.ts`** — introspected from the live Neon DB (`pnpm db:pull`), not hand-written. The DB had a full 46-table schema with seed data (products, offers, a Shopee provider) before this repo had any Drizzle code — re-pull after any out-of-band schema change instead of hand-editing shape.
- **`lib/db/client.ts`** — Drizzle over `@neondatabase/serverless`'s `Pool` (WebSocket, transaction-capable; required for the outbox-style writes in `docs/architecture.md`, not available on `neon-http`).

E-mail goes through Brevo only when `BREVO_API_KEY`/`EMAIL_FROM` are set; otherwise `sendResetPassword` just logs the link server-side.

New signups get **no role** (zero permissions) — grant one with `pnpm db:grant-role <email> <ROLE_CODE>`.

Migration tracking is baselined against the pre-existing schema — `db:migrate` is safe/idempotent.

### API route conventions (`app/api/v1/*`)

Every route handler follows the same shape via `lib/server/api.ts`:
- `ok(data, init?)` / `fail(message, status, details?, headers?)` — wrap responses as `{ data, meta }` / `{ error: { code, message, details? }, meta }`. `meta.mode` is now `'real'`.
- `authorize(request, permission)` — now **async**, returns `{ blocked: Response | null, userId: string | null }`. Reads the real Better Auth session from `request.headers` (`auth.api.getSession`), then checks the permission via `lib/auth/permissions.ts`. No session → 401; session but missing permission → 403. Callers must `await` it: `const { blocked } = await authorize(request, 'catalog:write'); if (blocked) return blocked`.
- `jsonBody<T>(request)` — unchanged, safe JSON body parse.

**Not every route calls `authorize()`** — public catalog reads (`GET /products`, `GET /products/{id}`, `GET /offers`, `GET /providers`) are intentionally anonymous (mirrors the old mock's `x-mock-role` defaulting to `viewer`, which always had `catalog:read`). Mutations and anything ops/analytics-flavored stay gated. Idempotency (`Idempotency-Key` header) is backed by the real `idempotency_keys` table via `lib/db/idempotency.ts#withIdempotency()`, not an in-memory map.

### `proxy.ts` (root)

Next 16 renamed edge middleware from `middleware.ts` to `proxy.ts` (exports `proxy(request)` + `config.matcher`). Here it only stamps `x-request-id`/`x-trace-id` onto `/api/:path*` and `/admin/:path*` requests for correlation — no auth or redirect logic lives here.

### Admin panel (real, all backed by the database)

`app/admin/[module]/page.tsx` renders `components/admin/module-screen.tsx` for each entry of `lib/admin-config.ts` (the single module registry: slug, group, and a `view`). `admin-shell.tsx` gates access client-side (no session → `/entrar`, no role → `/`), and every API route re-checks the permission server-side; the client check only decides what the menu shows (`permissionForModule` in `lib/auth/rbac.ts`).

Four building blocks, so a new module is usually a few lines:
- **Resources** (`lib/admin/resource-meta.ts` isomorphic field metadata + `lib/admin/resources.ts` server handlers + `lib/admin/validate.ts`): generic list/create/update/delete over `app/api/v1/admin/resources/[resource]` and `.../[id]`, rendered by `components/admin/resource-manager.tsx`. Every mutation goes through `lib/admin/guard.ts` (permission, validation, `recordAudit()` into `audit_logs`, cache invalidation via `lib/db/invalidate.ts`). To add a resource: add it to `resources`, write a `Handler`, register it in `handlers`, add the module in `admin-config.ts`.
- **Settings** (`lib/admin/settings-defs.ts` + `lib/settings.ts`, stored in `global_settings`): `seo`, `theme`, `home`, `ranking`, `slots`, `tracking`. Definitions carry defaults, so a key never saved behaves exactly like before. The storefront reads them with `getSetting()` (5-min cache, tag `settings`): metadata and robots (`app/layout.tsx`, `app/robots.ts`), theme tokens (`StorefrontShell` + `lib/theme.ts`, which derives hover/ink tones and enforces 4.5:1 contrast for the action color), home texts/section order (`app/page.tsx`), ranking weights and the similar-products slot (`StoreDataProvider`, `lib/recommendation/settings.ts`, `/api/v1/recommendations`), disabled events (`/api/v1/events`, `/api/v1/outbound-clicks`, `/api/v1/engagement`).
- **Editorial lock**: `products.editorial_locked`. Editing a product in the panel (name, status, categories, tags, description) sets it, and `importCatalogItem()` then only refreshes Shopee-owned data (rating, index, offer, price history, image). Without it the daily import would overwrite every edit. "Ocultar" archives (`status = removed`) and locks; nothing is hard-deleted.
- **Public content from the panel**: `campaigns` (home banner with a date window, `components/home/campaign-banner.tsx`), `coupons` (`/cupons`), `content_pages` (articles at `/artigos/[slug]`, pages at `/p/[slug]`, rendered by the HTML-free `components/content/markdown.tsx`), `curated_collections` (merged into `buildCollections()` through `StoreCatalog.curated`, ordered by the panel). The storefront reads them from `lib/db/repositories/site-content.ts` (cached, tag `catalog`, date windows applied at read time). Menu and footer only show Cupons/Artigos/pages when there is published content (`getStorefrontNav()`).

**Coupons — what the Shopee API really offers.** The affiliate GraphQL API has no coupon or voucher data (`productOfferV2`, `shopOfferV2`, `shopeeOfferV2`, `conversionReport`, `validatedReport`, `partnerOrderReport`, `listItemFeeds`, `getItemFeedData` only). So coupons are registered by hand (code, discount label, validity, affiliate link) and `POST /api/v1/admin/coupons/sync` imports the official category campaigns from `shopeeOfferV2` as `source = 'shopee_campaign'`, hidden until staff renames and shows them (names come in English). The sync never overwrites title or visibility after the first import. Never present these as coupon codes.

`segments` are saved rules over `affiliate_clicks` (reach = distinct sessions in the window, computed on the fly in `segmentReach()`); they are an analysis tool, not on-site targeting. Feature flags (`feature_flags`) only have effect for keys the code reads (`wiredFlags` in `resource-meta.ts`; today `cupons`), and the UI says so per key. Import runs are recorded in `sync_jobs`/`sync_job_runs`/`sync_errors` by `lib/providers/shopee/run.ts`; Logs shows failed runs and dead jobs; the LGPD module lists `privacy_requests`.

The storefront's design tokens (`--primary`, `--surface`, `--foreground`, `--success`, `--radius-*`, `--shadow-*`, `--ease`...) are defined once on `.store` in `components/storefront/storefront.module.css` (applied by `StorefrontShell`). One color per role: orange (`--primary`) is the only action color, green (`--success`) is only for savings/success, navy (`--foreground`) is text and brand. New storefront UI should use a CSS Module that reads those tokens — don't add hex colors. Existing modules: `home`, `featured-products`, `product-detail`, `search-experience`, `personal-pages`, `content-pages` (auth, prose, 404/error), `account`.

`app/globals.css` is legacy: it was pruned by measurement (selectors whose classes appear nowhere in `app`/`components`/`lib` were removed) and now mostly serves the admin and a few shared classes (`.product-card` family in `ProductCard`, `.btn`, `.container`, `.sr-only`). `ProductCard` keeps its global class names on purpose — e2e tests select by them (`.product-card`, `.product-buy-button`, `.product-sold-count`, `.product-card-link`). Playwright's config uses `localhost` on purpose: the Next dev server blocks its own chunks for `127.0.0.1` and hydration fails.

Consent and e-mail (both real now): storefront events (`favorite_*`, `compare_updated`, `product_viewed`, ...) leave the browser only when `garimpo:cookie-preferences.analytics` is true (`lib/platform/consent.ts`, enforced in `lib/platform/services.ts#tracker`; admin operations are not gated), and `@vercel/analytics` is mounted by `components/consented-analytics.tsx` only after that consent. Password reset sends e-mail through Brevo's HTTP API (`POST /v3/smtp/email`) when `BREVO_API_KEY` (or the legacy `brevo`) and `EMAIL_FROM` are set (`lib/auth/email.ts`); without them the link is only logged and `/recuperar-senha` says so. The new-password screen is `/redefinir-senha`. Personalization is real but narrow and **on-device**: the home's "Para você" tab (`components/home/home-catalog.tsx`) appears only when `cookiePreferences.personalization` is on **and** there is something to learn from — interests the visitor actually saved (`VisitorState.preferencesSaved`; the defaults in `defaultPreferences` never count) and/or at least `MIN_SIGNALS` products they viewed, favorited or compared (`lib/personalization/affinity.ts`: favorite weight 3, compare 2, recent 1 with decay; category 50%, brand 12%, price-band fit 14%, quality 24%; already-favorited items are excluded and just-seen ones are demoted). The profile is computed in the browser from `localStorage` and never sent to the server. Nothing else in ranking reads `state.preferences`. LGPD self-service lives in `/conta#dados`: `GET /api/v1/me/export` (own data only) and Better Auth's `deleteUser` (enabled in `lib/auth/auth.ts`; password required when the account has one; DB FKs cascade or set null). Google-only accounts delete with a fresh session and no password. There is still no human channel for requests that can't be self-served.

### Operations: catalog freshness, caching, clicks

- **Catalog refresh**: The daily import runs on a **VPS worker** (`worker/importer.ts`, Docker image `garimpo-importer`, 06:00 America/Sao_Paulo; steps in `worker/README.md`), not on Vercel Cron (`vercel.json` has no `crons`). The worker bundles only `lib/db`, `lib/providers/shopee` and 3 npm deps, runs `runCatalogImport()` (same code as `pnpm db:import-shopee`; records each run in `sync_job_runs`), then calls `POST /api/v1/cron/revalidate` with `Bearer $CRON_SECRET` so the site invalidates `catalog`/`metrics`. `GET /api/v1/cron/shopee-import` (same secret via `lib/server/cron-auth.ts`) stays as a manual/alternative trigger; without `CRON_SECRET` both routes answer 503. The import prunes products outside the selection only when the run covered >=70% of the current catalog. A full run (11 categories, ~264 products) takes ~2–4 min; the manual route has `maxDuration = 300`, the VPS worker has no limit. Categories and their search terms live in `categoryGroups` (`lib/providers/shopee/import.ts`); adding one also needs a checklist in `lib/catalog/guides.ts` (it works without one, with an empty list). Collection pages use `PagedProductGrid` (24 at a time, up to 120).
- **Caching**: `getStoreCatalog()` / `getProductMetrics()` use `unstable_cache` (5 min) and fall back to a direct DB read outside the Next runtime (tests, scripts). Product and category pages use `revalidate = 300`. The client context gets `toClientCatalog()` (no gallery/long description/full price history); the product page reads the full item server-side.
- **Affiliate clicks**: buy buttons stay direct links (`rel=sponsored`). `components/affiliate-click-tracker.tsx` is one delegated listener on `a[data-offer-id]` (buy buttons), `a[data-coupon-id]` (coupons) and `a[data-campaign]` (home banner); with `analytics` consent it POSTs `/api/v1/outbound-clicks` or `/api/v1/engagement` (item + slot + a per-tab id, no IP/UA/user). New buy buttons must carry `data-offer-id` and `data-slot`.
- **Real commissions**: `lib/providers/shopee/conversions.ts` reads `conversionReport` (paginated by `scrollId`; the API only looks back 3 months, so the window is clamped to 89 days) and `conversions-run.ts#runConversionSync()` upserts into `affiliate_conversions` + `affiliate_conversion_items` (idempotent on `(provider_conversion_id, provider_id)`; `paid` is never downgraded; the order number is stored only as a hash). Status: `PENDING→pending`, `COMPLETED→approved`, `CANCELLED→cancelled`, any item with `fraudStatus` FRAUD→`rejected`. Imported rows have no `click_id` (Shopee does not return ours); they reach a product through the items' `itemId` = `offers.external_id`, and reach a channel through `sub_ids` (the report's `utmContent`). `validatedReport` is not used: it needs a `validationId` that only the payout panel exposes. The VPS worker runs it after every import and every `CONVERSIONS_EVERY_MIN` (default 180) minutes; also `pnpm db:sync-conversions [--days=60]`, `node importer.mjs --conversions`, and `POST /api/v1/admin/conversions-sync` (`jobs:run`, button in Analytics). Runs are recorded in `sync_job_runs` with job type `conversion_sync`. `GET /api/v1/admin/commissions?days=` feeds the "Comissões reais" panel (by status, origin and product). At the time of writing the account had 0 conversions in the last 90 days, so the field mapping beyond the schema is covered by fixtures, not by real data — recheck `utmContent`/`netCommission` semantics against the first real sale.
- **Tagged affiliate links**: the buy button's `offers.affiliate_url` is a `generateShortLink` link carrying sub ids `site` + the category slug (`lib/providers/shopee/links.ts`; `offers.affiliate_sub_ids` records which tag the stored link has, so it is generated once per offer and regenerated only when the tag changes). Shopee only accepts **letters and digits** in sub ids (hyphen/underscore → error 11001; `bem-estar` becomes `bemestar`) and reports them joined by `-` (`site-tecnologia---`). If link generation fails the import falls back to the API's raw `offerLink` (still earns commission, just untagged) and retries next run. `SHOPEE_TAGGED_LINKS=0` turns it off. Future channels (Telegram etc.) call `generateShortLink(url, ['telegram', '<campaign>'])` at post time so the commission report separates them.
- **Coupon clicks**: `lib/db/repositories/coupon-clicks.ts` aggregates `analytics_events` `coupon_click` (metadata `couponId`) per coupon; shown as columns in the coupons list and as a summary above it (`GET /api/v1/admin/coupons/report`, `catalog:read`). Counts only visitors who accepted analytics consent and only within the events retention window — a floor, not the real total.
- **Image upload from the panel**: `POST /api/v1/admin/uploads` (`content:write`, multipart field `file`) validates the file by its **magic bytes** (JPG/PNG/WebP/AVIF/GIF only, so an SVG/HTML renamed to `.png` is refused; limit 4 MB because Vercel functions cap bodies at 4.5 MB), stores it in Vercel Blob under `uploads/YYYY-MM/<uuid>.<ext>` and writes an audit entry. `components/admin/image-upload.tsx` is the button next to any URL field flagged `upload: true` (`ResourceField` / `SettingField`: campaign and coupon images, SEO share image). `adminFetch` only sets the JSON `content-type` for string bodies, so FormData keeps its boundary.
- **Editable catalog rules** (`rules` setting, panel: Experiência → Regras do catálogo): `lib/catalog/rules.ts` holds the thresholds (viral/top/loved sales, find price/rating/sales, promo and heavy discount, premium price, top/perfect rating, value score/price) with the original numbers as defaults. `buildCollections({ ...catalog, rules })` and `matchesSignal(signal, product, offers, rules)` take them, and collection titles/descriptions are generated from the same numbers, so text never diverges from the rule. Server pages read them with `getCatalogRules()` (`lib/catalog/server-rules.ts`); client components read `useStoreData().rules` (set in `app/layout.tsx`). The `ate-20/50/100` budget collections stay fixed because the number is part of the slug.
- **Editable guide checklists** (`guides` setting, panel: Conteúdo → Guias de compra): one textarea per category, one check per line as `Título | Texto` (max 6, 60/280 chars). An empty category keeps the text in `guideChecklists` (code); `getGuideChecklists()` feeds `buildGuide({ ...catalog, checklists })`. The setting's default is the serialized code text, so the editor starts from what the site shows today.
- **LGPD requests and consent**: `POST /api/v1/privacy-requests` (public, no account needed; per-IP limit + 100/hour global cap + honeypot field `website`) writes to `privacy_requests` (`user_id` is now nullable; new columns `email`, `message`, `source`, `response_note`; enum gained `correction`/`information`/`revocation`/`other`) and returns an 8-char protocol. Queue and internal note live in Painel → LGPD (`lib/admin/resources.ts#privacyHandler`, joins users only when there is one). `POST /api/v1/consent` stores each cookie choice in `consent_records` (identifier `garimpo:consent-id` in localStorage, created only when a choice is made; only changed categories are written). Both are called from `/privacidade` / `VisitorStateProvider`; neither depends on analytics consent.
- **Staff invites**: Painel → Usuários e papéis → "Convidar para a equipe" (`lib/auth/invites.ts`, table `admin_invites`, `users:manage`). The token is 32 random bytes (base64url) stored only as a SHA-256 hash; the link is `/convite/<token>` and is shown **once** (plus e-mailed through Brevo when `emailEnabled()`). Validity 7 days, one pending invite per e-mail (a new one revokes the old), only an OWNER can invite OWNER/ADMIN. The invitee signs in or signs up with the **same e-mail** (`/entrar?next=…` and `/cadastro?next=…` honour `lib/auth/redirect.ts#safeRedirect`, same-site paths only) and accepts at `POST /api/v1/invites/accept`; the role is granted in `user_roles` inside a transaction that claims the invite (`accepted_at is null`), so two clicks cannot accept twice. The public lookup `GET /api/v1/invites/<token>` returns only a masked e-mail, the role and the status. 
- **MFA (two-factor, TOTP)**: Better Auth's `twoFactor` plugin (`lib/auth/auth.ts` / `client.ts`), tables `two_factor` + `users.two_factor_enabled`. Users turn it on in `/conta#seguranca` (password → QR code → first code → recovery codes shown once); sign-in then answers `twoFactorRedirect` and `AuthForm` sends the visitor to `/verificar` (TOTP or recovery code, optional "trust this device 30 days"). Confirming the first code makes Better Auth **issue a new session cookie** — any code that keeps the old cookie after enabling gets 401. `ADMIN_REQUIRE_MFA=1` makes `authorize()` (lib/server/api.ts) answer 403 `{ code: 'MFA_REQUIRED' }` to OWNER/ADMIN without it; **off by default** so the team enables first and enforcement comes after. `/api/v1/me` returns `mfa: { enabled, required, enforced }` and the admin shell shows a banner. Lost phone and codes: `pnpm db:disable-2fa <email>`. Known gap: the plugin's hook covers e-mail/password sign-in; Google sign-in is not challenged, so enforce MFA only together with disabling Google for staff or accept that path.
- **Visual site editor** (Painel → Home, `components/admin/site-builder/*`): ported from the nextrotta CMS in concept and UX (editor, history, drag-and-drop, library, zoom, click-to-select, global design), written for Garimpo's own document model. A **document** (`lib/site-builder/document.ts`) is an ordered list of sections `{ id, type, name, hidden, archived, settings }` plus optional `page` (SEO title/description) and `design`. *Built-in* types (`hero`, `campaign`, `catalog`, `selections`, `guides`, `howItWorks`; one each, only on the home) keep pulling real data and expose only texts; *free blocks* (`banner`, `text` Markdown, `cards`, `image`, `imageText`, `faq`, `collection` = first 8 products of a catalog collection, `cta`, `spacer`) show what staff typed. Every section also has **appearance** (`background`, `color`, `padding`, `width`): built-ins accept only light backgrounds and never change text color (validated, so the dark navy text stays legible); free blocks auto-pick a readable text color from the background (`lib/site-builder/visual.ts`) and the editor warns below 4.5:1. `archived` removes a section from the page without deleting it (counts toward the 40-section cap; a built-in that is archived cannot be added twice). Three kinds of document, all in `site_documents` (`key`, `draft`, `published`, `history` of the last **30** publications): `home`; `page:<slug>` (pages created in the panel, served at `/paginas/[slug]`, free blocks only, born as draft/off-air, can be unpublished and — only when off-air — deleted, in the sitemap when published); and `global` ("Aparência do site": `design = { theme: { primary, radius, font }, header: { noticeText, noticeDetail }, footer: { tagline, signature, links[≤8] } }`, `lib/site-builder/design.ts`). Without a published `global`, the site keeps using Configurações → Tema (`defaultDesign(theme setting)`), so nothing changes until someone publishes; the palette is deliberately short (one action color with the same 4.5:1 rule as the Tema panel, 3 corner presets, 3 font stacks) because the storefront keeps one color per role. The layout reads it through `resolveStorefrontConfig()` (`lib/site-builder/storefront-config.ts`, cached with tag `site-documents`). Editor behaviour: undo/redo with grouped typing (`lib/site-builder/history.ts`, pure, 60 steps, Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y, Ctrl+S flushes), pure operations in `lib/site-builder/operations.ts` (move/insert/duplicate/archive/restore/delete, all unit-tested), HTML5 drag-and-drop in the list and from the library (buttons remain for keyboard), component library with search, zoom (fit/50/75/100) and device width, **click-to-select in the preview** (same-origin iframe of `/?preview=1` or `/paginas/<slug>?preview=1`; sections carry `data-cms-section`, header/footer carry `data-cms-global` and jump to "Aparência"), autosave (900 ms, serialized PUTs) with a `localStorage` recovery copy (`garimpo:cms-recovery:<key>`) and a `beforeunload` guard, version panel. The preview is the real server render with the draft: it reloads after each save keeping the scroll (not live-while-typing). `?preview=1` is honoured only for `content:write` (`lib/site-builder/preview.ts`) and also applies the **draft** global design through a nested `StorefrontConfigProvider`. API: `GET/POST /api/v1/admin/site-documents` (pages index + collections list / create page), `GET/PUT/POST/DELETE /api/v1/admin/site-documents/[key]` (state, save draft, `publish|discard|restore|unpublish`, delete page); every mutation audited, publish invalidates `site-documents`/`settings`/`catalog`. Tests: `tests/unit/site-editor.test.ts`, `tests/integration/site-documents.test.ts` (own keys `teste-…`/`page:teste-…`; the real `home`/`global` are never written), `tests/e2e/site-editor.spec.ts` (reads `home` and `global`, creates/deletes its own page). Not done: scheduled publishing, canvas drag (drag works in the list), live typing in the preview, extra palette colors, legal texts (they are Painel → Páginas, Markdown).
- **Operational health** (`lib/ops/health.ts`): four checks read from the real tables — catalog import freshness (latest of `catalog_import` success and `offers.last_synced_at`; warn > 30 h, critical > 54 h), commission sync (warn > 8 h, critical > 26 h), failed background jobs in 7 days, and pending LGPD requests (warn at 10 days, critical at 15). Panel: block at the top of `/admin`; `GET /api/v1/admin/health` (detail, `catalog:read`); `GET /api/v1/health` (public, only `{ status, checkedAt }`, **503 when critical**, so an external uptime monitor — UptimeRobot, Better Stack — can alert on any 5xx). Nothing pushes a notification by itself yet: an external monitor on `/api/v1/health` is the cheapest way until the Telegram bot exists.
- **Price drops on favorites** (`lib/favorites/price-drops.ts`): the browser stores the price at the moment each favorite is first seen (`garimpo:favorite-prices`, never overwritten) and `VisitorStateProvider` exposes `priceDrops` (drop ≥ 2% and ≥ R$ 1 vs today's `currentPrice`). Shown in `/favoritos` and the `/conta` shortcut. Local only: a favorite synced to a new device starts a new baseline; no e-mail yet.
- **Engine (foundation, no AI yet)**: Painel → Engine (`components/admin/engine-view.tsx`). Pure rules in `lib/engine/rules.ts` turn numbers into `ProposalDraft`s; `lib/engine/store.ts` persists them in `engine_proposals` (`shadow | pending | applied | rejected | failed | expired`), de-duplicates by `(kind, subject_id)`, honours a 30-day cool-down after a rejection, and applies them; `lib/engine/run.ts#runEngine()` ties it together and is called by the worker after import + commissions, by `pnpm engine:run` and by the panel's "Rodar agora". **No imports from `next/*` in `lib/engine`** (the worker bundles it). Modes (`engine` setting): `off`, `shadow` (default; records only, cannot be approved), `approval`, `auto` (applies only `AUTO_KINDS` = `import_term`). Two rules today: (1) *catalog pruning* — proposes archiving products with no clicks/favorites/conversions after a minimum age, **only when the site had ≥ `minSiteViews` product views in the window** (otherwise it explains there is not enough data), capped per run and by share of the catalog; applying = `status removed` + `editorial_locked` + offers removed, never a delete; (2) *seasonal radar* — `lib/engine/calendar.ts` computes Brazilian commercial dates (Easter, Mother's/Father's Day, Black Friday…) and proposes importer terms inside each date's lead window; an approved `import_term` is read by `runCatalogImport()` via `activeSeasonalTerms()` and added to that category's searches until its `until` date. At the time of writing the site had 0 measured product views in 30 days, so pruning is idle by design.
- **Telegram posting queue** (`lib/social/*`, Painel → Postagens, table `social_posts`): `compose.ts` writes the message **only from real offer numbers** (price, Shopee's previous price when it exists, rating, sales; never invented urgency) with five templates chosen by product id, escaped for Telegram HTML, plus a fixed affiliate disclosure; `picker.ts` ranks active offers (editorial score, real discount, 30-day price drop, sales; commission is only a soft tie-breaker and never shown) with eligibility (rating ≥ 4.5, sales ≥ 100, image, 14-day cool-down, one per category per batch); `schedule.ts` spreads `dailyLimit` posts across the window in Brasília time (UTC−3, no DST); `telegram.ts` calls the official Bot API (`sendPhoto` with fallback to `sendMessage`, honours 429 `retry_after`, errors never carry the token); `store.ts` creates posts (link via `generateShortLink(url, ['telegram', campaign])`, so commissions appear as `telegram-<campaign>` in Analytics), approves, cancels and delivers; `run.ts#runSocialQueue()` plans today's slots (`autoPlan`), expires stale pending posts and sends the due ones. Env: `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` — **without both nothing is sent**, posts just sit in the queue. Defaults are conservative: setting `social.mode = off`, `requireApproval = true`, 4 per day, 9h–21h. A post more than 3 h past its time is marked failed instead of sent late; delivery claims the row first (`attempts` compare-and-set) so the worker and the panel button can't double-send; transient errors retry up to 3 times. The worker runs it every `SOCIAL_EVERY_MIN` minutes (default 5; 0 disables). Tests must scope `deliverDue`/`expireOldPending` by campaign — they act on every due post otherwise.
- **AI copy for posts (DeepSeek)**: `lib/ai/deepseek.ts` (key from `DEEPSEEK_API_KEY` or the lowercase `deep_seek` already in `.env`; model `deepseek-chat`; no `next/*` imports) and `lib/social/rewrite.ts`. The model only changes **tone and structure**: the prompt carries public offer data only (name, price, optional previous price, rating, sales, link — never visitor data), and `validateRewrite()` rejects any answer that lacks the exact link or price, cites a number absent from the facts or the product name, mentions a discount without a real previous price, uses urgency/scarcity/guarantee phrases (`bannedClaims`, Unicode-aware lookarounds — `\b` does not work with accents), adds other links/hashtags/mentions, or exceeds Telegram's limit. A rejected answer falls back to the fixed template (reason kept in `facts.ai`); the affiliate disclosure is appended by code, never by the model. Used when `social.useAi` is on (new posts) or via the "Reescrever com IA" button (`PATCH /api/v1/admin/posts/[id]` `{ action: 'rewrite' | 'restore_text' }`, the previous text is kept in `facts.originalText`). Live-checked against the real API on 2026-10-13. Cost: ~300 tokens per post.
- **A/B tests of the home hero copy** (`lib/experiments/*`, Painel → Testes A/B, table `ab_experiments`): one test running at a time; variant A is always the live hero, B overrides any of title/accent/text/button. The server always renders A; `components/home/hero-copy.tsx` assigns the variant **in the browser and only with analytics consent** (`assignVariant(visitorId, key, splitB)`, FNV-1a bucket, stable per `garimpo:ab-id`), swaps the text if B and reports one exposure per tab (`POST /api/v1/experiments/exposure`, only for the *running* key). Buy-button clicks carry `experiment = <key>-<a|b>` (read from `sessionStorage`) into `affiliate_clicks.sub_id`, which is how conversions are attributed. Metric = distinct sessions with a buy click ÷ distinct exposed sessions (Shopee never says which visit produced an order, so this is click-through, not sales). `compare()` is a pooled two-proportion z-test and refuses a verdict below 200 exposures per variant. Window start/stop use the **database clock** (`now()`), because app/DB clock skew silently cut recent events. "Aplicar B ao rascunho da home" copies B into the home draft via `applyHeroCopy` (you still publish). Without consent nobody is bucketed and nothing is stored.
- **Collections and guides are real**: computed from the catalog on each revalidation (`lib/catalog/collections.ts`, 16+ in 5 groups (plus one per category: 11 categories today — tecnologia, casa, audio, cozinha, bem-estar, pet, beleza, fitness, games, eletronicos, eletrodomesticos) — Em alta: viralizou (10k+ sales), mais-vendidos, queridinhos, achadinhos; Preço: em-promocao, desconto-pesado, ate-20/50/100, acima-de-500 (most sold among items from R$ 500); Qualidade: bem-avaliados, custo-beneficio (same criterion as the /buscar filter), nota-maxima; Por categoria: mais-vendidos-<categoria>; plus manual ones created in the panel (`curated_collections`, group Curadoria; need >=3 active products to appear and may not reuse an automatic slug). No data source says what is viral on TikTok, so never label a rule-based collection that way; `lib/catalog/guides.ts`: one guide per category with >=3 products, plus a short buying checklist authored in code). They reuse `matchesSignal` so counts match `/buscar`. Pages: `/colecoes`, `/colecoes/[slug]`, `/guias`, `/guias/[slug]`; they appear in the menu, footer, home and sitemap. Manual curation lives in `curated_collections`; free-form pages live in the visual editor.
- **Admin**: see *Admin panel* above. `/admin` shows real numbers from `lib/db/repositories/admin-overview.ts`; imports run from `/admin/imports-jobs` (`POST /api/v1/admin/catalog-import`, permission `jobs:run`, same `runCatalogImport()` as the cron). `/admin/catalogo` redirects to Produtos.
- **RUM**: `components/consented-analytics.tsx` mounts Vercel Analytics and Speed Insights only with `analytics` consent. **Tests DB**: set `TEST_DATABASE_URL` to point `pnpm test` at a separate Neon branch.
- **Site URL**: `lib/site.ts#siteUrl` (`NEXT_PUBLIC_SITE_URL`, else Vercel's production domain, else localhost). Never hard-code a domain.
- **Search/category SSR**: `SearchExperience` takes params by props (no `useSearchParams`) so the grid is in the HTML; `/buscar` reads `searchParams`, `/categorias/[slug]` is static and applies the URL after mount.
- **E2E**: `pnpm test:e2e` (dev server) or `pnpm test:e2e:prod` (build + `next start` on :3000, so stop `pnpm dev` first — the auth client bakes `NEXT_PUBLIC_BETTER_AUTH_URL=http://localhost:3000` into the build, and on another port the panel never sees the session; faster and deterministic). `tests/e2e/admin-modules.spec.ts` logs in as a **real** OWNER (`tests/e2e/helpers/admin-session.ts`: Better Auth sign-up + role row, cookie applied to the context, users deleted afterwards) and walks every module of `adminConfigs` on desktop and mobile, failing on runtime/console errors, load-failure states or page-level horizontal overflow — add a module to `adminConfigs` and it is covered automatically. `playwright.config.ts` loads `.env` and strips the Brevo keys so no e-mail can leave.
